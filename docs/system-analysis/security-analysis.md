# Security analysis

Scope: local passive analysis, Phase 1 authentication, Phase 2 catalog and Phase 3 orders and Phase 4 payment settlement foundation, Phase 5 inventory integration, and Phase 6 staff management + typed settings + immutable audit. This is not an OWASP compliance claim or provider integration review. Relevant framework behavior was checked against installed Laravel 13 and [official Sanctum documentation](https://laravel.com/framework/docs/13.x/sanctum).

## Assets and trust boundaries

1. Untrusted Flutter/native/Web input -> Laravel HTTPS JSON API: credentials, tokens, identifiers, query/body properties are hostile until authenticated/validated/authorized. UI permission hints never grant access.
2. Laravel -> MySQL: application account handles identity and authoritative finance/stock; Eloquent parameter binding, narrow fields, FKs, uniqueness and transactions protect this boundary. Flutter has no database credentials or connection.
3. Future Laravel <-> provider: provider credentials remain backend-only; notifications are untrusted until official verification; compare exact settlement facts. External I/O cannot share an atomic SQL transaction.
4. Deployment/CI -> configuration: .env and keys are ignored; fixtures are synthetic. Production debug/TLS/cache/proxy settings require operational review. Third-party documents/logs grant no execution authority.

## Threat and control register

| Boundary / abuse path | Impact | Implemented evidence/control | Remaining mitigation / regression |
| --- | --- | --- | --- |
| Credential guessing / address enumeration | Staff impersonation | LoginRequest bounds; 5/min per email+IP plus 30/min per IP; hashed keys; generic 401 for wrong/missing/inactive/unassigned accounts; dummy hash check for missing user | Production TLS/trusted proxy config; shared cache on multiple nodes; tests invalid identity and limit recovery |
| Stolen/expired token replay | Authorized data access | Sanctum SHA-256 token storage, eight-hour expiry, current-token logout, active-account middleware, no-store responses; Phase 6 admin-controlled token revocation and password reset revoke all account tokens | Secure native storage / first-party Web cookie+CSRF in later client milestone |
| Role/active/permission injection | Admin escalation | Strict login properties; User mass assignment excludes role_id/is_active; fixed gate map with no admin global bypass; Phase 6 staff provisioning/updating uses strict Form Requests, approved enum roles, and row-locked last-admin protection | Self-action cannot bypass last active admin rule; test role spoofing, unknown roles and role changes |
| ID substitution / BOLA | Other staff order/payment disclosure | Scoped own/shop lookup plus OrderPolicy/PaymentPolicy/cancellation reauthorization; two-actor denials tested; UserPolicy restricts staff management to admins | Maintain object policies on new actions |
| Function authorization bypass | Cashier changes catalog/stock/settings | Active staff/ability middleware, catalog/manage-catalog and inventory/adjust-inventory policies, management-only recipe/ledger writes, admin-only manage-staff and manage-settings policies | Operational settings readable by managers; all mutations restricted to admins |
| Excess serialization | Password/token hash leakage | UserResource, StaffResource, SettingResource, and AuditEventResource fields explicitly selected; User hides password/remember_token; token plaintext only on login response | Tests assert absence of passwords, token hashes, and secrets from all API responses and audit metadata |
| SQL injection / mass assignment | Data modification/disclosure | Eloquent bound email lookup; validated intended fields; SettingRegistry allow-lists `shop_name` and `shop_timezone`; arbitrary/secret keys return 422 | No client-defined SQL/sort/role |
| Duplicate checkout/payment/movement replay | Duplicate settlement/physical deductions | Actor/order keys and request hashes, provider identity UQ, deterministic sale key; atomic transactions and real MySQL replay races | No public callback contract; real provider/durable worker remain gated |
| Fake payment / wrong merchant/amount/currency | Unpaid goods / misapplied funds | Exact server/provider fact matching, persisted uncertainty/evidence, review guard before local finalization; injected client proof rejected | Fake-only verification; official provider authentication required before network integration |
| Concurrent stock changes | Oversell / corrupt ledger | Recipe/product synchronization, sorted stock row locks, exact reservations, unique movement identities, atomic ledger/balance/order updates and 14 MySQL races | Read-only consistency reports drift; no automatic repair/expiry |
| Secret/debug/log exposure | Token/credential compromise | No seeded users/secrets, ignored .env, token/credential fields never intentionally logged by new code | Production APP_DEBUG=false, HTTPS, redact Authorization/password and provider payloads at proxy/APM/app; review log collectors; secret rotation is separate scope |

Likelihood depends on public exposure and deployment; impacts on staff identity and future money are material even at shop scale. Rate limits share an IP across shop devices, so an identity/IP limit is complemented by a higher IP cap and avoids permanent account lockout. File-cache counters are a local baseline; review atomic/shared counters under measured concurrency before production expansion. Proxy trust is deliberately not broadened in this milestone.

## Implemented versus planned

Phase 4: object-scoped payment APIs, strict tender/empty-proof body contracts, per-order key/hash, 30 operations/minute actor limit, exact integer cash/provider amounts, immutable provider observations and owning-order composite FKs. Provider evidence is fetched outside transactions and all provider/order/correlation/merchant/amount/currency/identity facts must match before acceptance. Two orders cannot claim one transaction; paid selection cannot be replaced by stale models. Extra or mismatched received-fund evidence is retained/quarantined. Credentials/keys/hashes/merchant/raw verification payloads are omitted from Resources. No public callback authenticity claim or real KHQR provider exists; production adapter fails closed. Manual recovery is not a durable worker. See [payment contract](../api/payments.md) and [Phase 4 evidence](phase-4-verification.md).

Phase 3 adds process-pos checkout and OrderPolicy plus scoped queries (hidden/missing refs share 404). Only validated product IDs/quantities reach the service; both top-level and nested property injection are denied. Header keys are bounded ASCII and actor-scoped; canonical hash excludes prices/credentials. Shared catalog locks, unique winner comparison after rollback, checked exact cents and all-or-nothing item writes are verified on MySQL. Resources expose only authoritative snapshots and authorized creator id/name, never key/hash/credentials. History limits, strict absolute boundaries and eager relationships address input/query abuse. Phase 4 payment controls are detailed below; Phase 5 inventory controls follow below; receipt printing remains future work. The MySQL session now explicitly uses UTC; legacy timestamp interpretation must be audited before rollout where old sessions were non-UTC.

Implemented: bearer-only Sanctum config (no cookie guard/stateful middleware/CSRF-cookie route), required staff token ability, fixed role gates, user-view policy, live account/role checks, strong field boundaries, resources, secure hash verification/rehash, finite expiry, token revocation, JSON errors/throttling, no-store auth responses/API errors and tests. No public registration/reset/staff-edit API. Factory credentials are explicitly synthetic and seeders create only roles.

Implemented Phase 3 order policies and query scoping are detailed below. Implemented core exact provider facts/idempotency/observations/quarantine, tested via fake only. Planned: real provider authentication/callback integration and durable worker/recovery, admin audit log, password recovery/token inventory, backup/restore verification and client secure storage. Production TLS/secrets/logging are operating requirements, not verified deployment controls. No outbound calls or real payment tests are authorized/performed.

Phase 2 implemented: Category/Product Policies reuse view-catalog/manage-catalog gates; every catalog route uses existing Sanctum/active-staff/staff-ability middleware. Strict create/update/query Requests reject privilege/owner/internal fields. Cashiers cannot mutate any catalog ID and cannot read retired details; managers/admins can manage the shared shop catalog. Products belong to categories via RESTRICT FK. Resources serialize only approved catalog fields and a minimal eager-loaded category summary. Integer-cent string validation rejects floats, negative/oversized/noncanonical prices and unsupported currency. SKU database uniqueness is authoritative, including a collision after request validation (422). Search binds escaped literal patterns; sort is fixed; pages are capped at 100 items and page 10000. No caching or raw client SQL identifiers. See [Phase 2 checks](phase-2-verification.md).

## Phase 5 inventory security review

Balance/available/reserved/actor/order/sale/operation/tracking injections are rejected. Strict exact strings and checked native integer arithmetic prevent float coercion and overflow. Gates and policies restrict metadata/recipe/manual movement/ledger to management, while stock availability is readable by active staff. Scoped cancellation preserves cashier ownership; unresolved/active/review payment denies release. Shared finalization checks persisted owning confirmed payment, exact order amount and no reconciliation requirement before stock effects.

Product locks synchronize recipes and checkout; sorted inventory locks serialize reserve/adjustment/consumption/release. Actor-key and deterministic sale uniqueness prevent physical effects on replay. Stock ledger and reservation facts cannot be overwritten via ordinary model/API updates. Local failure rolls back payment/order/stock as a unit; trusted remote funds still require reconciliation after local rollback. No secret/raw provider logging, real provider traffic or public callback was added. Read-only consistency diagnostics do not repair balances; raw DBA tampering remains an operational boundary. See [Phase 5 checks](phase-5-verification.md).

## Phase 6 staff, settings, and audit security review

Staff management endpoints (`/api/v1/staff`) are guarded by `auth:sanctum`, active staff middleware, and `manage-staff` permission (UserPolicy). Cashiers and managers cannot access any staff mutation or viewing endpoints (403). Input payloads are strictly validated using `RejectsUnknownFields`: role must be an allowed `StaffRole` enum value (`cashier`, `manager`, `admin`), email is trimmed and normalized to lowercase, and direct `role_id` injection is rejected. Email unique collision is handled at the database level and caught as 422 Unprocessable Content.

Token revocation policy is enforced by `StaffManagementService`: role changes, email changes, deactivations, and password resets immediately delete all Sanctum personal access tokens for that user account. Name-only updates safely preserve active sessions. Reactivations do not auto-issue tokens.

Last operational admin protection is enforced under row-level database locking (`Role::where('name', 'admin')->lockForUpdate()`), preventing concurrent demotion/deactivation races from leaving zero active administrators. Both multi-process MySQL races and single-process logic checks confirm that reductions from 1 to 0 active admins return 409 Conflict.

Operational settings (`/api/v1/settings`) enforce allow-listing through `SettingRegistry`. Only `shop_name` (string, max 120) and `shop_timezone` (valid IANA timezone) are accepted. Secret keys (`APP_KEY`, `DB_PASSWORD`, `INVENTORY_TRACKING_ENABLED`) and arbitrary schema-free keys return 422. Settings updates are restricted to admins; managers have read-only access; cashiers are denied.

Audit events (`/api/v1/audit-events`) record sensitive administrative actions (`staff.created`, `staff.updated`, `staff.role_changed`, `staff.activated`, `staff.deactivated`, `staff.password_reset`, `staff.tokens_revoked`, `setting.updated`). The `audit_events` table is append-only; the `AuditEvent` Eloquent model registers `updating` and `deleting` hooks that throw `LogicException` on any mutation attempt. Audit metadata is structured JSON that never records passwords, hashes, or secret tokens. Audit logs are queryable only by admins, with indexed filtering by actor, action, subject, and date range. See [Phase 6 verification](phase-6-verification.md).
