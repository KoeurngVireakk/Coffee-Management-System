# Backend implementation plan

## Phase 1: authentication and access foundations (this milestone)

Add Sanctum compatible with installed Laravel 13, additive migrations for roles/user access/token table, standard-role seeder with no staff accounts, synthetic factories, LoginRequest, UserResource, Api/V1 AuthController, active staff middleware, role gates and UserPolicy. API: POST login, POST logout, GET me under `/api/v1/auth`. Fixed eight-hour bearer expiry; no refresh/registration. Tests assert success, 401/403/422/429, expiry/revocation, forbidden properties, role changes, sensitive fields and data constraints. Update actual API contract and OpenAPI specification.

Rollout: verify dedicated database and backup existing data; `php artisan migrate`, then `php artisan db:seed --class=RoleSeeder` (or root seeder). Never guess privileges for legacy accounts; all stay inactive/unassigned until trusted provisioning. No account/password is generated by seeding. Review any factory use as test-only. Later staff provisioning/password recovery is Phase 6; for initial local development use an explicit synthetic factory pattern described in database guidance, never a public bootstrap-admin endpoint.

## Technical conventions

- Follow existing Laravel layer boundaries; Eloquent/Requests/Resources/Policies solve CRUD. A checkout/payment service is justified by orchestration/transactions, not by an abstract repository pattern.
- Use additive migrations; inspect deployed data and backup before schema change. MySQL-specific CHECK/locking/collation features require isolated MySQL tests; SQLite is a fast feature-test target, not proof of those semantics.
- No provider call inside a database transaction. Persist intent first, reconcile crashes, use bounded retry only with proven replay safety. Introduce durable queue/worker only alongside a real recovery workflow.
- For each milestone synchronize implemented endpoints/OpenAPI/requirements status, run focused negative-path tests, Composer gates and route inventory, then architecture/database/security/QA/Git self-review.
- Keep Flutter/UX out of this task. Future Flutter auth must decide native secure storage, Web cookie/CSRF, navigation/state handling and accessible error feedback without moving backend authority into UI.

Official references: [Sanctum](https://laravel.com/framework/docs/13.x/sanctum), [authorization](https://laravel.com/framework/docs/13.x/authorization), [MySQL locking reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html). Framework APIs are also checked against installed vendor source; provider semantics await its current official contract.
